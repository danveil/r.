# Rayang Partner View — engineering report

This records the v0.2 implementation baseline. Its Safari-first pairing instructions are superseded by the [v0.2.1 portable handoff report](PARTNER-HANDOFF-REPORT.md) and the updated security/deployment guides. Do not rely on Safari state transferring into a Home Screen installation.

Implemented and locally validated on 9 September 2026. Ready for staging validation; not deployed or certified for physical iPhone use. All test histories were synthetic. The original application's live browser data was not accessed.

1. **Baseline.** Existing React 19/TypeScript/Vite PWA with Dexie v1, local date-only predictions, four primary screens, JSON backup/restore and offline support. Baseline: 72 unit/interaction tests and 14 browser tests. The initial source tree was uncommitted/untracked and has been preserved; no reset, commit or push was performed.
2. **Modules.** Added `src/partner/{protocol,snapshot,crypto,api,storage,service,PrimarySync,SharingSettings,PartnerView}` and CSS; protocol/API/sync tests; development fixtures; `server/{partner-api,blob-store,testing}`; API/cleanup Netlify Functions; local API helper and browser sharing journeys. Updated entry routing, App sync, Settings, import/delete guards, Vite worker configuration, Netlify configuration, test scripts, dependencies/lockfile and documentation.
3. **Backend choice.** Netlify Functions plus durable site-scoped Blobs with strong consistency and conditional ETag writes. This fits the existing host without a second database/account provider. A SQL or full authentication service would add setup beyond the small capability-based relationship. The local helper uses an ephemeral CAS store; production never does.
4. **Threat model.** Protect against guessed IDs, stolen storage contents, unauthorized mutation, replayed/claimed invitations, stale writes after revocation and accidental private-field uploads. Device compromise, malicious served JavaScript, copied capabilities, metadata leakage and already received copies remain explicit limits. Architecture was documented before implementation in [PARTNER-SECURITY.md](PARTNER-SECURITY.md).
5. **Pairing.** Explicit primary consent and independent categories; locally generated QR or equivalent `/partner#invite=…` link. The fragment holds version, opaque ID, invitation capability and encryption key, and is removed when initial JavaScript runs. Ten-minute pending lifetime, one successful claim; the same persisted reader may retry a lost acknowledgment. Partner reviews categories and explicitly accepts. Opening a pending invitation downloads/decrypts its preview; any holder of that invitation can obtain the initial snapshot, even before pressing Accept.
6. **Encryption.** Native Web Crypto AES-256-GCM, fresh random 96-bit IV for each encryption, 128-bit tag, relationship/version-bound AAD. Strict validation before encryption and after authenticated decryption. Plaintext limited to 32,000 bytes, API body to 48,000 bytes. No homemade cipher or server-side decryption.
7. **Keys.** Independent random 256-bit key, ID and write/invitation capabilities; partner generates its own 256-bit read capability. Raw endpoint keys persist in separate IndexedDB so offline decryption works; operations import non-extractable CryptoKey handles. No key in query strings, API payloads, ordinary exports, analytics or application logs. Device storage is not a hardware keychain. Re-pairing rotates all material.
8. **Authorization.** SHA-256 capability hashes at rest and constant-time comparisons. Writer may create/publish/revoke and inspect status; invitation may preview/claim; reader may fetch active ciphertext. The partner receives no write token. Exact API route and operation/method/content-type/size checks; same-origin policy, bounded client fetch, generic denials, configured platform IP/domain rate limit. No primary mutation API exists.
9. **Payload.** Snapshot schema v1: generated timestamp, date, three grants, optional phase/cycle-day/actual-period state, estimated period range, optional fertile/ovulation dates, and at most 42 date/flag calendar cells. Calendar grants are independent. Fertile/ovulation phase labels are withheld without the fertility grant. No record IDs, arbitrary strings, full settings or full history.
10. **Private exclusions.** Diary, symptom/mood/flow tags, private notes and ovulation observations are neither serialization inputs nor calculation inputs to the snapshot builder. Tests use throwing getters to detect accidental access. Full backups/recovery copies never enter the sharing path.
11. **Sync.** Foreground launch/resume, online recovery, meaningful cycle snapshot changes and manual Sync now. A timestamp-independent local fingerprint suppresses diary-only uploads. Off means no sharing API calls. No polling, push or background synchronization. Partner reads on opening, foreground and manual refresh; it displays snapshot time and stale/offline state without recomputing primary estimates.
12. **Revocation.** Atomic ciphertext-free tombstone blocks future authorized reads and publication; conditional writes prevent stale mutation from reviving it, including cancellation racing with creation. Offline stop remains visibly pending and blocks uploads/new pairing until acknowledged. Partner authorization failure clears credentials/cache. Active shares expire after 30 days without publication; daily cleanup removes expired ciphertext and seven-day tombstones. Earlier in-flight responses and offline/copied information cannot be recalled.
13. **Partner UI.** Warm existing design language; read-only Home, bounded Calendar and Settings, explicit freshness, actual versus estimated markings, neutral disconnected/error states, install guidance and local disconnect. No diary, editing, logging, insights or full-data export controls. Synthetic phase/limited/stale/offline/revoked fixtures are development-only and never sync.
14. **Primary Settings.** Default-off section, unchecked category controls, explicit encrypted-sharing explanation, QR/link alternative, selected categories, pending/active status, last sync, retryable errors, manual sync and confirmed stop. Changing categories requires stop/re-pair with fresh credentials.
15. **IndexedDB.** Original `rayang-private` schema remains version 1. New `rayang-partner` v1 has primary connection, partner connection/encrypted cache and role preference tables. Existing records are not migrated or rewritten. Populated v1 records survived reopen/integration checks. Import/delete requires confirmed sharing stop; backup schema/content remains unchanged.
16. **Service worker.** Still precaches only static assets, now including lazy partner modules. API and Functions navigation routes are denied SPA fallback interception; no runtime health-response cache. Browser tests confirm no API/invitation cache entries and successful root/standalone-style Partner View launch after total server shutdown.
17. **Headers.** Restrictive self-only CSP/connect policy, no-referrer, anti-framing, nosniff, denied camera/microphone/geolocation. API responses carry private/no-store browser and Netlify CDN headers; bearer capabilities stay in Authorization. Platform response handling must still be checked after deployment.
18. **Tests.** **117 passing tests across nine Vitest files**: original 72 plus 45 new. **62 passing tests per timezone** in UTC, Asia/Kuala_Lumpur and America/New_York (186 executions, not additional unique tests). **20 browser tests pass**, ten each Chromium/WebKit, including original journeys, two-device sharing and actual offline server loss. Axe reports zero violations on the original primary screens/diary and Partner Home in both engines. Strict TypeScript, ESLint and formatting pass; production npm audit reports zero vulnerabilities. [Detailed QA](QA.md)
19. **Build.** Production Vite build passes. API and scheduled cleanup entry points also bundle successfully for Node 22. Actual Netlify deployment/runtime binding is not claimed by this local bundling check.
20. **Bundle.** Main JS: 368.80 → **371.29 kB raw**, 116.85 → **117.68 kB gzip** (+0.83 kB gzip). Primary CSS unchanged at 4.84 kB gzip. Lazy additions: Partner View 3.62, service 4.08, Settings/QR 12.15 and partner CSS 0.57 kB gzip. Worker cache: 16/~410 → **20/464.81 KiB** entries/uncompressed size. Optional code can be cached while sharing is off; it does not trigger health uploads.
21. **Deployment.** Git-connected Netlify, Node 22, `npm run build`, `dist`, both Functions and durable Blobs. HTTPS required for real devices. Use separate staging and production sites; site-scoped storage persists across deploys. Verify scheduling, actual strong conditional storage, headers and edge rate limiting on staging. [Deployment checklist](PARTNER-DEPLOYMENT.md)
22. **Environment.** **No new custom environment variables.** Netlify injects server-side platform storage authorization. No application master encryption key or user account is required. No secret should be supplied as `VITE_*`.
23. **Remaining manual steps.** Connect/publish the repository, inspect rate-limit processing, exercise the hosted API/storage/cleanup checklist with synthetic information, replace the existing repository-link placeholder and confirm the existing license before publication. No external service or recurring automation was created.
24. **Physical iPhones.** Test both installations, Safari-to-Home-Screen pairing persistence, standalone role routing, QR scanning, date picker/keyboard, safe areas, VoiceOver/dynamic text, offline reopening, sync/revocation, Files export/import and actual installed update delivery. Full primary and partner lists are in the deployment guide.
25. **Limits.** Anyone holding a pending invite can preview; first claimant wins future read capability. Readers can clone credentials, copy or screenshot data. The backend lacks endpoint keys, but a compromised host can replace JavaScript. Device access/XSS defeats endpoint protection; primary backups remain readable. IP/timing/size metadata is visible. Clock rollback may reject new snapshots as older. Browser storage loss can orphan access until expiry. Rate limiting is not a spending cap; large cleanup workloads and platform backups may delay physical deletion. No independent audit or actual phone certification is claimed.
26. **Future ideas, not implemented.** Independent protocol review, stronger device-bound key storage, an explicit multi-device design, authenticated monotonic revision counters, scalable cleanup/rate-abuse controls, and encrypted primary backups. No accounts, symptoms sharing, remote primary editing, full-history cloud backup or other product expansion was added.

## Explicit privacy answers

| Question                                           | Answer                                                                                                                                                       |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Did existing Rayang data survive migration?        | No source migration was needed; populated v1 records survived automated reopen checks unchanged. The live user browser database was not accessed or altered. |
| Is sharing-off still local-only?                   | Yes. No sharing API requests or health uploads; ordinary static app/update downloads still occur.                                                            |
| Can the backend decrypt shared health information? | Not from its stored records: it never receives the encryption key. Compromised replacement client code remains a documented trust boundary.                  |
| Can a partner modify primary data?                 | No. They receive no writer capability and there is no remote primary-record mutation API.                                                                    |
| Is diary or symptom data transmitted?              | No. These fields never enter the allowlisted snapshot, including its calculation inputs.                                                                     |
| Can a revoked partner receive future updates?      | Not after confirmed revocation. Offline revocation is pending; earlier authorized in-flight responses, caches and copies cannot be erased retroactively.     |
