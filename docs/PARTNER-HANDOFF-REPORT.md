# Partner setup handoff — v0.2.1 engineering report

Implemented on 10 September 2026. This fixes the reported iPhone storage-context assumption; it does not force Safari to launch an installed app. Local browser validation is separate from the physical-iPhone steps below.

**Later status, recorded 10 September 2026:** user-reported physical iPhone verification passed for Safari invitation → setup code → Home Screen Rayang → import/accept → Partner View → close/reopen persistence → primary update synchronization → revocation → old-code rejection. This supersedes the pending status in item 28. Codex did not independently perform physical-device testing. The original implementation results below are retained as history; [FINAL-HARDENING.md](FINAL-HARDENING.md) records the subsequent hardening pass.

1. **Root cause.** The previous flow claimed the invitation and stored the reader/key in Safari, then assumed the installed PWA would find that record. The root launcher only checks its own IndexedDB. The user's physical test demonstrated a separate Home Screen context; our independent-context test now reproduces that boundary without copying storage.
2. **Existing architecture.** Baseline commit `8d93ede` already contains Partner View, 117 unit/integration tests and 20 browser tests. A ten-minute invitation contains v1 ID/invitation capability/key in a fragment; the accepting client generates a reader. The server stores ciphertext and capability hashes. Primary writers, readers and invitations have separate authorization.
3. **Handoff architecture.** A portable client-only setup code re-encodes the existing **unclaimed invitation**. Safari only previews categories and offers copying. The installed app validates/imports it and claims through the unchanged API.
4. **Why.** All necessary material is already in the fragment. No new table, migration, endpoint, token exchange, account, service, dependency or backend state is needed. The final reader is generated in the destination context, so Safari cannot consume it first through this UI.
5. **Format.** `RAYANG1-<base64url-canonical-JSON>.<base64url-SHA256>`. JSON is exactly `{version:1,id,invitation,key}`. SHA-256 covers the prefix plus encoded payload. A 1,200-character bound, exact fields/version, canonical encoding/JSON and 32-byte lengths are checked before network access. The checksum detects copying errors; it is **not authentication**. Algorithms remain fixed by existing v1 AES-256-GCM.
6. **Cryptographic material.** Existing independent 256-bit share ID, invitation capability and decryption key. The installed app creates its own new 256-bit reader during acceptance; the code does not need a reader capability. Missing invitation capability is therefore the applicable missing-access-secret validation case.
7. **Excluded material.** No primary writer, full invitation URL, plaintext menstrual snapshot, period history, diary, symptoms, mood, notes, settings, primary database or backup. Extra algorithm/read/write/health fields are rejected.
8. **Writer exclusion.** Yes: exact-field validation and tests prohibit a writer field. The primary copy control explicitly constructs an Invitation; it never serializes a primary connection record.
9. **Key stays client-only.** Yes. Neither the setup code nor key is sent to the API, request URL, headers, referrer, cookie or logs. Browser-network assertions inspect both handoff/destination contexts. Existing invitation/read Authorization values and read hashes still reach the backend for their original purpose; the server is unchanged.
10. **Browser mode.** Dedicated warm Partner Setup screen, selected categories, native installation instructions, Copy setup code and manual-copy fallback. No Accept action and no persisted reader. Copy requires a click; there is no automatic clipboard write, read or clearing. The visible URL becomes `/` while the invitation remains in page memory. After reload, reopen the original link to derive the same code while it remains valid.
11. **Standalone mode.** Central `display-mode.ts` checks the standalone media query or iOS navigator hint. A direct invitation can be reviewed/accepted without copy/paste. A pasted code is validated, previewed/decrypted and accepted locally. These hints guide presentation, not authorization/device binding. [MDN standalone guidance](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/How_to/Create_a_standalone_app)
12. **Fresh PWA.** Welcome → I have a partner setup code → paste → Continue → review → Accept Partner View. No menstrual onboarding is needed. The root launcher subsequently reads the installed context's own role/credentials.
13. **Existing PWA.** Primary Settings includes Set up Partner View on this device. Existing primary records trigger explicit acknowledgment; none are deleted/rewritten. Partner Settings can return to the primary cycle. Existing partner records can still open in their original context.
14. **Storage separation.** No Safari IndexedDB/localStorage/sessionStorage transfer. Codes are transient UI memory/clipboard, never persisted in a new handoff store. Destination credentials/cache use the existing partner table; primary tables remain unchanged. Tests start context B with no records or storage from context A.
15. **Lifecycle.** Preview does not claim. First acceptance saves a generated reader before the request; successful cache decryption precedes storing the active role preference. Failed requests can retry with the same saved reader, including after reload. Pending invitation expiry remains ten minutes and does not restart when copied. Only the first distinct reader claims it.
16. **Revocation.** Unchanged server tombstones and capability checks block future synchronization. Reimporting a revoked code cannot restore the relationship. Offline revocation remains pending and already received copies/caches cannot be recalled.
17. **Service worker.** No rule changes. New setup modules are ordinary precached assets; no setup codes, fragments, capabilities or API responses enter Cache Storage. Update prompts are suppressed during setup to avoid discarding the in-memory code. Existing encrypted/offline partner behavior still passes.
18. **Manifest/router.** Manifest ID, start URL and scope stay `/`; standalone display unchanged. Added non-secret `/partner/setup` entry, root browser handoff routing and explicit `#primary` return. Existing Netlify SPA fallback already serves these routes. Local test helpers were extended for the new setup path. No custom URL scheme, Universal Link, dynamic manifest or server-visible secret path was added.
19. **Compatibility.** No IndexedDB version change or source-data migration. v0.2 invitation fragments are supported; existing reader records remain usable in their original context. Already claimed Safari-only v0.2 relationships cannot be converted back into unclaimed invitations: those legacy installations need one fresh invitation for the new destination. New browser handoffs avoid that trap entirely.

## Required physical-iPhone acceptance sequence

1. On the primary phone, generate a fresh invitation with synthetic data and chosen categories.
2. Open it on the partner's iPhone in **Safari**. Confirm Partner Setup, visible root URL and no Accept button. Copy the setup code explicitly; test manual copy if the API is denied.
3. If needed, use Safari Share → Add to Home Screen → Add Rayang. If already installed, reuse that installation. Do not accept/claim in Safari or rely on its database transferring.
4. Open Rayang **from Home Screen**. Choose I have a partner setup code, or the existing Settings setup action. Paste → Continue → review categories → Accept. If primary history exists, verify the warning/acknowledgment and unchanged history.
5. Close the installed app completely, reopen from Home Screen, and verify the same Partner View. Then test Airplane Mode reopening with the cached snapshot.
6. Return online. Change a synthetic period on the primary, Sync now, and refresh the installed Partner View. Verify the new date/cycle day and actual/estimated treatments.
7. Revoke on the primary, refresh the installed partner, and confirm inactive state. Paste the old code again; access must remain denied.
8. Test expired/truncated codes, offline setup, native paste, VoiceOver/dynamic text, safe areas, existing-install route, and direct standalone invitation where iOS permits it. Remove saved code copies and replace clipboard contents afterward.
